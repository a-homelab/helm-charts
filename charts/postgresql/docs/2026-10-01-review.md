## Findings and decisions

The Netail chart supplies declarative databases and inline application roles,
plugin ObjectStores and schedules, checksum-enabled bootstrap, recovery, and
external-secrets credential generation/escrow. Its EKS IAM, scheduling, storage,
and credential assumptions do not fit the existing Ceph homelab installations.
Those provider-specific defaults were not copied.

The homelab chart now exposes additive options for those PostgreSQL features,
while preserving existing credentials and Ceph archives. Improvements beyond
both original charts include multiple Database resources, native schemas/FDWs,
DatabaseRole resources, external/operator TLS, explicit PodMonitor ownership,
image catalogs/digests, native bootstrap and additional Cluster fields, snapshot
schedules, values validation, and repeatable compatibility/schema checks.

New settings override equivalent old values. Legacy configurations remain
supported without requiring a migration. In particular, old pod labels and
topology selectors are frozen together: CNPG compares topology constraints when
deciding whether to roll pods. The stable selector is an explicit opt-in.
Verified against the deployed operator's
[pod comparison implementation](https://github.com/cloudnative-pg/cloudnative-pg/blob/v1.28.1/pkg/specs/podspec_diff.go).
Digest image references retain their version tag because CNPG
[derives the PostgreSQL major from it](https://github.com/cloudnative-pg/cloudnative-pg/blob/v1.28.1/api/v1/cluster_funcs.go).

## Current upstream targets

- [CNPG 1.30.1](https://github.com/cloudnative-pg/cloudnative-pg/releases/tag/v1.30.1),
  released September 23, is the latest stable release verified here. It adds the
  DatabaseRole path introduced in 1.30. Its supported Kubernetes range is 1.34-1.36;
  1.31 is tested but unsupported. A supported deployment requires a separate
  platform upgrade. See the [support matrix](https://cloudnative-pg.io/docs/1.30/supported_releases/).
- [Barman Cloud plugin 0.15.1](https://github.com/cloudnative-pg/plugin-barman-cloud/releases/tag/v0.15.1),
  released September 30, is the latest stable plugin verified here. Native Barman
  removal is planned for CNPG 1.31. Follow the
  [migration procedure](https://cloudnative-pg.io/plugin-barman-cloud/docs/migration/)
  and prove recovery before declaring the archive migrated.
- [Database management](https://cloudnative-pg.io/docs/1.30/declarative_database_management/)
  supports extensions, schemas, FDWs, and servers, but not user mappings.
  Database changes reconcile on generation changes, and creation-only SQL fields
  cannot be used to rename or recreate existing databases in place.
- [Role management](https://cloudnative-pg.io/docs/1.30/declarative_role_management/)
  supports gradual adoption. Role attributes and memberships must be explicit
  during transfer; defaulting them can change existing privileges.
- [Monitoring guidance](https://cloudnative-pg.io/docs/1.30/monitoring/)
  deprecates operator-created PodMonitors. The chart provides separate ownership
  and a distinct resource name, with migration opt-in.

Generated credentials now use CNPG-owned Secrets with ESO Password generators
and Merge targets, following the
[CNPG integration](https://cloudnative-pg.io/docs/1.30/cncf-projects/external-secrets/).

with restricted read permissions and retains the copies independently of the
ExternalSecrets. Physical recovery remains native CNPG bootstrap recovery.
Local extraction/sanitization scripts were copied from the compared Netail commit,
marked untested, bound to localhost, and require an explicit compatible image.

An optional superuser client Certificate and a new TLS profile are implemented.

The intermediate separates signing identity but root-based PostgreSQL client
verification still shares trust with sibling local CAs. Existing issuers, HBA
rules, Secrets, and consumers remain unchanged. The new profile and credentials
require explicit activation; no live resources were changed.

Validation: 48 PostgreSQL behavior/template tests, 55 resource/schema checks,
26 cert-issuers tests, and all nine legacy consumer comparisons passed. These
include all eight live cluster identities. Credential templates were evaluated
with special-character test passwords using Helm's Go/Sprig engine; actual ESO

## Upstream refresh and chart 0.2.2, 2026-10-02

Release state, from GitHub releases and the
[support matrix](https://cloudnative-pg.io/docs/1.30/supported_releases/):
CNPG 1.30.1 (operator chart 0.29.1) is the latest release and the only supported
minor. 1.28 reached end of life on June 30 and 1.29 on September 29; the live
1.28.1 operator misses the 1.28.2-1.28.4 security and failover fixes. 1.31 has no
tag or release candidate, and in-tree Barman is still present on `main`.
PostgreSQL 14 support ends 2026-11-12; three live clusters run 14.4.
Barman Cloud plugin 0.15.1 remains current, with no ObjectStore schema change
since 0.13.

A field-level diff of the 1.28.1 and 1.30.1 CRDs found additions only:
`serviceAccountName`, `podSelectorRefs`, `primaryLease`, extension `bin_path`
and `env`, `projectedVolumeTemplate.defaultUser`, and in-tree
`restoreAdditionalCommandArgs`. All reach the chart through `clusterSpec` or
`postgresql`. The DatabaseRole spec and CEL rules match the chart's assumptions.

Chart 0.2.2 changes, all opt-in or limited to modes no consumer uses:

- The chart PodMonitor also selects `cnpg.io/podRole: instance`, matching the
  operator's own monitor. Without it, Pooler pods, which carry `cnpg.io/cluster`
  and a `metrics` port, would be scraped as database instances
  ([v1.30.1 podmonitor.go](https://github.com/cloudnative-pg/cloudnative-pg/blob/v1.30.1/pkg/specs/podmonitor.go)).
- Metrics TLS (`monitoring.configuration.tls.enabled`) makes PodMonitor endpoints
  default to HTTPS with the server CA and `<cluster>-rw` server name.
- `backup.serverName` sets the Barman plugin archive name, which upstream uses to
  separate archives across major upgrades
  ([postgres_upgrades](https://cloudnative-pg.io/docs/1.30/postgres_upgrades/)).
- `replicationSlots` merges over the fixed HA default, exposing
  `synchronizeLogicalDecoding`, `synchronizeReplicas` and related settings.
- `tls.serverAltDNSNames` adds server SANs for extra services or poolers.
- The README no longer says a major image change is inert: since CNPG 1.26 it
  starts an offline in-place `pg_upgrade`. It also states ESO 2.11.0 refresh
  behavior from the controller source: with `Periodic`/`0s` and `Orphan`,
  template changes never reach existing Secrets, deleted targets are not
  recreated, and recreating an ExternalSecret writes a new password.

All ten consumer values files render identically to chart 0.2.1 apart from the
chart version label. Validation passed 82 behavior tests and 67 schema checks,
including a temporary fixture with every new option.

## Decisions and chart follow-up, 2026-10-02

Ben's decisions after the upstream refresh:

- Pre-migration safety net: logical `pg_dump` archives in
  `~/Projects/zitadel-backups`, next to the earlier Zitadel dump. Scheduled base
  backups are not a precondition for the next stages.
- Kubernetes 1.31.14 is accepted for CNPG 1.30 although upstream supports only
  1.34-1.36. The Kubernetes upgrade remains separate.
- Deferred, not scheduled: PostgreSQL minor updates for every cluster (14.4,
  15.4, 15.7 and 16.2 are 2022-2024 releases) and major upgrades away from 14
  before its 2026-11-12 end of life (Home Assistant, LLDAP, Vaultwarden). Use the
  README "Major upgrades" procedure, which needs the plugin `backup.serverName`.
- Backups move to the Barman Cloud plugin. The manifests repository now has a
  manual `plugin-barman-cloud` Application (chart 0.8.1, plugin v0.15.1) in
  `cnpg-system`; consumers switch `backup.provider` one at a time afterwards.
- Argo CD health checks: the community check for CNPG Database first ships in
  Argo CD v3.6.0-rc1 ([argo-cd#29511](https://github.com/argoproj/argo-cd/pull/29511));
  the cluster runs v3.3.7. Do not maintain local copies; until an upgrade, verify
  `status.applied` and `observedGeneration` manually. Pooler, DatabaseRole and
  ScheduledBackup have no upstream check.

Chart 0.2.2 additionally:

- Requires `image.tag` or `imageCatalogRef`; the `15.3` default is gone. Every
  consumer already pinned a tag.
- Renders ESO targets with `immutable: true` unless rotation is enabled, so a
  recreated ExternalSecret cannot overwrite a password (ESO v2.11.0 skips
  templating an existing immutable target). Enabling rotation needs a one-time
  deletion of the immutable Secret; the README lists the procedure, which is
  derived from source and not yet exercised.
- Adds `poolers`. CNPG 1.30 still automates the PgBouncer `auth_query` login only
  when it holds the client CA key, which cert-manager Secrets lack. The chart
  therefore issues a `cnpg_pooler_pgbouncer` client certificate and sets the
  Pooler auth fields; the role and `user_search` function remain a one-time
  manual SQL step per cluster, because `managed.roles` and DatabaseRole reserve
  the `cnpg_` prefix. CNPG does not drop them for non-automated poolers.

Validation: 91 behavior tests and 66 schema checks, now including pinned 1.28.1
and 1.30.1 Pooler CRDs. All ten consumer values files still render identically
apart from the chart version label.

## cnpg-ca default and plugin certificates, 2026-10-02

Ben chose cnpg-ca as the default CA. Chart 0.2.3 defaults `tls.profile` to `cnpg`.
All nine deployed consumers already pin `tls.profile: legacy` with
`apps-ca-issuer`, so their renders are unchanged; each moves to cnpg-ca during the
migration plan. Firezone, whose Application is disabled, would start on cnpg-ca.

The manifests repository adds Certificate and ClusterIssuer `cnpg-ca` in
cert-issuers and installs the Barman Cloud plugin as a second source on the
cloudnative-pg Application, with its server and client certificates issued by
cnpg-ca from a third source, as in the netail-ai and ProlificLabs layouts. The
plugin chart's own templates can only reference a namespaced Issuer. The plugin
runs two leader-elected replicas spread across hosts.

The plugin loads the whole client `tls.crt` as its trusted client CA pool
([cnpg-i-machinery v0.4.2 server.go](https://github.com/cloudnative-pg/cnpg-i-machinery/blob/v0.4.2/pkg/pluginhelper/http/server.go)).
cert-manager writes the leaf and cnpg-ca there, so any client certificate cnpg-ca
signs passes the plugin's TLS check, unlike upstream's self-signed pair. Network
reachability of port 9090 in `cnpg-system` is then the remaining control.

## cnpg-ca moves to the estate domain, 2026-10-03

Before any sync, Ben moved cnpg-ca from `cluster-local-ca` to the estate's
`k8s-clusters-ca`, matching netail-ai: a CloudNativePG replica cluster on another
Kubernetes cluster verifies the primary's server certificate and presents a client
certificate the primary maps to a role, so both clusters' cnpg-ca must chain to the
common estate root. Clients now trust it through `homelab-root-ca`. PostgreSQL's
root-anchored client verification therefore accepts client chains from any estate
CA, still subject to HBA rules and certificate-to-role mapping.
