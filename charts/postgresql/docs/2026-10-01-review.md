## Findings and decisions

The Netail chart supplies declarative databases and inline application roles,
plugin ObjectStores and schedules, checksum-enabled bootstrap, recovery, and
external-secrets credential generation/escrow. Its EKS IAM, scheduling, storage,
and credential assumptions do not fit the existing Ceph homelab installations.
Those provider-specific defaults were not copied.

The homelab chart now exposes additive options for those PostgreSQL features,
while preserving existing credentials and Ceph archives. Improvements beyond
both original charts include multiple Database resources, native schemas/FDWs,
DatabaseRole resources, external/operator TLS, explicit PodMonitor ownership,
image catalogs/digests, native bootstrap and additional Cluster fields, snapshot
schedules, values validation, and repeatable compatibility/schema checks.

New settings override equivalent old values. Legacy configurations remain
supported without requiring a migration. In particular, old pod labels and
topology selectors are frozen together: CNPG compares topology constraints when
deciding whether to roll pods. The stable selector is an explicit opt-in.
Verified against the deployed operator's
[pod comparison implementation](https://github.com/cloudnative-pg/cloudnative-pg/blob/v1.28.1/pkg/specs/podspec_diff.go).
Digest image references retain their version tag because CNPG
[derives the PostgreSQL major from it](https://github.com/cloudnative-pg/cloudnative-pg/blob/v1.28.1/api/v1/cluster_funcs.go).

## Current upstream targets

- [CNPG 1.30.1](https://github.com/cloudnative-pg/cloudnative-pg/releases/tag/v1.30.1),
  released September 23, is the latest stable release verified here. It adds the
  DatabaseRole path introduced in 1.30. Its supported Kubernetes range is 1.34-1.36;
  1.31 is tested but unsupported. A supported deployment requires a separate
  platform upgrade. See the [support matrix](https://cloudnative-pg.io/docs/1.30/supported_releases/).
- [Barman Cloud plugin 0.15.1](https://github.com/cloudnative-pg/plugin-barman-cloud/releases/tag/v0.15.1),
  released September 30, is the latest stable plugin verified here. Native Barman
  removal is planned for CNPG 1.31. Follow the
  [migration procedure](https://cloudnative-pg.io/plugin-barman-cloud/docs/migration/)
  and prove recovery before declaring the archive migrated.
- [Database management](https://cloudnative-pg.io/docs/1.30/declarative_database_management/)
  supports extensions, schemas, FDWs, and servers, but not user mappings.
  Database changes reconcile on generation changes, and creation-only SQL fields
  cannot be used to rename or recreate existing databases in place.
- [Role management](https://cloudnative-pg.io/docs/1.30/declarative_role_management/)
  supports gradual adoption. Role attributes and memberships must be explicit
  during transfer; defaulting them can change existing privileges.
- [Monitoring guidance](https://cloudnative-pg.io/docs/1.30/monitoring/)
  deprecates operator-created PodMonitors. The chart provides separate ownership
  and a distinct resource name, with migration opt-in.

## Credential and CA follow-up

Generated credentials now use CNPG-owned Secrets with ESO Password generators
and Merge targets, following the
[CNPG integration](https://cloudnative-pg.io/docs/1.30/cncf-projects/external-secrets/).
All password-bearing connection fields are refreshed and escaped, including both
FQDN URIs. Rotation is configurable but off. Read-only deployment inspection found
ESO 2.11.0 available and no Reloader deployment; consumer reload wiring remains
a prerequisite. PushSecret/Vault escrow was explicitly excluded by Ben.

Recovery mode copies only explicitly named same-namespace credential Secrets
with restricted read permissions and retains the copies independently of the
ExternalSecrets. Physical recovery remains native CNPG bootstrap recovery.
Local extraction/sanitization scripts were copied from the compared Netail commit,
marked untested, bound to localhost, and require an explicit compatible image.
Only bash syntax and shellcheck were run; pg_resetwal salvage is not a proven restore.

An optional superuser client Certificate and a new TLS profile are implemented.
The manifests repo declares cnpg-ca under the already Ready cluster-local-ca.
The intermediate separates signing identity but root-based PostgreSQL client
verification still shares trust with sibling local CAs. Existing issuers, HBA
rules, Secrets, and consumers remain unchanged. The new profile and credentials
require explicit activation; no live resources were changed.

Validation: 48 PostgreSQL behavior/template tests, 55 resource/schema checks,
26 cert-issuers tests, and all nine legacy consumer comparisons passed. These
include all eight live cluster identities. Credential templates were evaluated
with special-character test passwords using Helm's Go/Sprig engine; actual ESO
reconciliation and application reconnect behavior still need a deployment test.

## Values-schema follow-up

Preferred aliases now include native `instances` and `postgresql`, grouped
`credentials.existing` references, and `backup.objectBucket.storageClassName`.
Explicit new settings override the legacy aliases; `postgresql: {}` clears the
old object while null inherits it. Netail's database locale fields now also feed
generated initdb, and a native bootstrap continues to override that construction.
The legacy defaults remain intact in a compatibility section of values.yaml.

The README maps Netail's values to the preferred homelab schema. The chart keeps
native recovery and explicit backup-provider/schedule configuration rather than
adding Netail-specific mode, cloud, and Karpenter wrappers. A schema-only migration
fixture renders exactly the same resources as the legacy fixture. Existing live
consumer values were not edited during this naming change.

## Chart adoption and explicit credential ownership, 2026-10-02

Ben pushed chart commit `b316b02355244deb9fa723796df90b6895fa0068` and manifests
commit `ed0973c9a193ef14e81bf05abb4e5d7fb09025d5`, reconciled the parents and
manually synced all seven existing consumer Applications. Verification found
all eight PostgreSQL clusters healthy with three ready instances each, unchanged
Cluster specs and primaries, and unchanged identities for all 24 pods and 24 PVCs.
Database container restart counts did not increase, and WAL archiving remained
healthy. Harbor's PreSync migration container exited successfully but its ordinary
Istio sidecar kept the Job active; Ben stopped that completed Job's sidecar, after
which Harbor's sync succeeded and all its workloads became healthy.

The preferred values were already active in the initial manifests commit; only
their explanatory notes were comments. Keep legacy aliases during adoption and
edit the preferred keys when both forms coexist. The Codecov Database pilot was
prepared in manifests commit `9df1552f756f7fab797d5659f62f9642db36503e`.
No Database CRs were live when preparing the following naming correction.

Ben selected descriptive resource names based on actual SQL identities:
`<cluster>-db-<database>`, `<cluster>-role-<role>`, `<cluster>-creds-<role>`, and
`<cluster>-recovery-creds-<role>`. Kubernetes names normalize SQL punctuation and
case; SQL names remain unchanged. Explicit full-name overrides preserve already
deployed CR identities. Normalization collisions and names that exceed the chart's
63-character limit fail rendering instead of silently reusing or truncating names.

Ben explicitly prohibited CNPG-generated credential Secrets. The 0.2.0 Merge
implementation was never enabled in the live homelab. Version 0.2.1 replaces it
with ESO-controlled retained Secrets and explicit Cluster references. Generated
ExternalSecrets include matching usernames and all connection fields, use
`creationPolicy: Orphan` and `deletionPolicy: Retain`, and retain the existing
reload label and disabled scheduled rotation. Native bootstrap configurations
must include an explicit application credential reference. Superuser access
always requires an explicit superuser reference. Existing SealedSecret references
remain unchanged; no generated credentials are activated by this naming update.

This uses [explicit CNPG bootstrap credentials](https://cloudnative-pg.io/docs/1.28/bootstrap/#bootstrap-an-empty-cluster-initdb)
with [External Secrets password generation and reload](https://cloudnative-pg.io/docs/1.30/cncf-projects/external-secrets/).
ESO's [Orphan policy](https://external-secrets.io/latest/api/externalsecret/)
preserves target Secrets if an ExternalSecret is removed. Existing applications'
Secret names and data-key references need a separate credential migration;
Reloader integration and password rotation remain deferred.

Verification reports and SQL metadata for the Codecov pilot are in
`/tmp/cnpg-compatibility-rollout/`. Recheck Database applied/observed-generation
status, SQL identities and extension versions after Ben syncs the revised pilot.
The operator upgrade, new CNPG CA, role-management adoption and backup-provider
migration remain separate rollout stages.
